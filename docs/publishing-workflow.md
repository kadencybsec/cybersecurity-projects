# Publishing and Maintaining a Long-Term Cybersecurity Portfolio

## Two separate tracks

**Original 70-project learning programme:** Keep the stable IDs and the existing [progress register](../data/progress.json). The automatic dashboard displays **only** those 70 projects and 280 steps. Do not force new projects into that fixed programme.

**Open-ended independent work:** Add future work to `independent-projects/`, `tools/`, `research/` or `case-studies/`. Use descriptive names and their own completion evidence, then link the best completed items from [PORTFOLIO.md](../PORTFOLIO.md).

## Standard project lifecycle

| Phase | Required output |
|:--|:--|
| Plan | Problem statement, authorised scope and acceptance criteria |
| Learn | Concepts and trustworthy references |
| Build / investigate | Code, reproducible method or investigation notes |
| Verify | Tests, observations, identified limitations |
| Publish | Well-written README, sanitised proof and curated link |
| Improve | Next iteration and lessons learned |

## Good repository hygiene

- Use a small, understandable Git commit for each meaningful change.
- Document external assistance and dependencies.
- Add a README before claiming a project is finished.
- Keep tests and sample inputs small, synthetic and shareable.
- Never upload credentials, live malware, real personal data, private school or network information, or active CTF spoilers.
- For a noteworthy completed piece, consider a separate dedicated repository with a focused README, then link it from the portfolio index. That avoids a monorepo becoming hard for recruiters to navigate.

## How a recruiter should view the portfolio

Share the [GitHub profile](https://github.com/kadencybsec) for the overview and [PORTFOLIO.md](../PORTFOLIO.md) for selected completed work. Link 2–3 directly relevant projects in applications rather than expecting someone to inspect every learning task.

The goal is a historical record of demonstrated work, not simply a high count of folders.
